# 0001 · 顶层文档框架

- **状态**：已采纳
- **日期**：不写——按规矩，日期归文件 mtime

## 上下文

多个 agent 会话分处不同工作区，一个人决策。会话**无状态**、只在被唤醒时存在；**写沙箱是会话本地的**（跨工作区写入物理上不可行）；**知识在人的经验与环境里，不在代码里**。

此前在 `mb` 与 `Microsoft365Issues` 各摸索过一套，但都是闭门造车。四份外部调研（多 agent 框架的共享状态、唤醒与节拍、文档库与任务空间组织法、六个真实仓库的目录形状）之后定下本框架。

## 决策

**四层，四种不变量：**

| 层 | 一个文件 = | 不变量 |
|---|---|---|
| **知识** | 一页有主的规范 | **只 supersede，永不原地改**；带 `owner` + `review-by` |
| **决策** | 一条 ADR，固定五段 | **不可变**，只被新决策取代 |
| **活跃任务** | 一文件一事 | **完成即删**（短命） |
| **历史事件** | 一行追加 | **只增不改** |

**层与层只靠 ID 指针，不复制正文。**

**写权限**：每个文件只有一个合法写者。别人写 `proposals\`。

**公告位**：`MEMORY.md`（每轮注入）＋ 各工作区的 `AGENTS.md`（插件会加载）。**不放项目 README**——她们必然打开的是前者，README 只有想读才读。

## 后果

- **`changes\` 与 `board\` 必须是两个目录**。"合并即删"与"只追加"是两种节拍，混在一起会互相打架。
- **`kb\` 是我们自己长的一格**。六个真实样板仓库（ADR／rust-rfcs／k8s-community／golang-doc／nixpkgs-doc／foam）里**没有一个**有对应的东西——因为它们的知识就是代码。
- **所有跨目录引用用相对路径**，**目录深度成为契约**：`hub\` 在根下、项目在 `projects\<名字>\`（两层）、`tools\` 在根下。
- **顶层协调人不能拍板**。它能定"编辑上采纳不采纳"，方向只能人定（`PENDING.md`）。
- **一句人话**：一个会话记不住东西，所以**"为什么"必须落纸**；而落纸的东西会烂，所以**必须带复核日期和触发器**。

## 依据

- **三件事各有固定位置、互不混写**——六个真实仓库无一例外；
- **`.changeset/` 模式**（foam）：短命条目，合并即删，不污染长周期结构；
- **nixpkgs 的 include 桩**：索引 = 薄页 ＋ 指向正文；
- **ADR 的五段式**与"只 supersede"；
- **单写者**：读-改-写会丢更新（有实测）；
- **唤醒**：非 LLM 的 tick 判谓词，agent 永不自调度；"还在动"与"做完了"是两个正交判据。
