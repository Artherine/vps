## 决定

- **写台账的触发条件用上下文长度，不用日期、也不用轮数。**
  具体：比上一次记录时的上下文长度多出 **120,000 token** 就写一条；或者上下文绝对值超过 **600,000 token** 就写一条（兜底）；或者刚发生压缩就写一条，并把基线重置为压缩后的实测值。

  **为什么不用日期或轮数：** 因为压缩是按 token 量触发的，而每轮涨多少极不均匀——这一段 25 轮涨了 193,303，平均一轮七千七，但早期有一轮涨几万的。用日期或轮数当尺子，量不到真正的那条线。

  **为什么是 120,000：** 要保证"被压缩掉的内容一定已经记过"，**记录间隔必须小于压缩后保留的 token 量**。观测到的最小保留量是 181,533 token；扣掉静态注入的部分（系统提示、工具定义、注入的规则文件，估计两万上下）和压缩摘要本身（约一万八千 token），**真正留给对话的约十四万三千**（181,533 − 20,000 − 18,000 ≈ 143,500）。120,000 落在里面，余量约两万三。**这个余量不大，所以才有 600,000 那条兜底。**

- **台账分三类文件、两条轴。**
  三类是：`index.md`（常读的总索引）、`entries\`（按时间切的流水段）、`topics\`（按话题归拢的当前定论）。
  两条轴是：时间和话题互相独立。同一件事在时间轴上是"当时怎么定的"，在话题轴上是"现在是什么"。
  **为什么这样分：** 因为旧结论留在旧的流水段里，所以"这个定论变过"是可以看出来的——这正是压缩摘要做不到的事。

  **为什么不把原文抄进来：** 原文一直在会话日志里，按轮号能取到。抄进台账会造出第二份真源，而两份真源必然分叉。

- **不建自我文档。**
  曾经想过建一个 `hub\self\`，记录"我倾向于什么、什么时候它会从选择变成反射"。最终否掉了。

  **为什么：** 用纸面定义自己的个性和倾向，等于把"这篇上下文"换成"一份摘要"——**和这套系统要躲的东西是同一个**。而且信息会积累、环境会变，性格和习惯本来就会变；放任它变，比反复修正它更对。**自我不是写下来的，是读记录时归纳出来的。**

- **记账纪律做成技能，不写进 `MEMORY.md`。**
  因为 `MEMORY.md` 会被注入每一个会话，包括短命的子会话；子会话没有台账，也不需要。

- **技能放在 `C:\Artherine\DSH\.dsh\skills\ledger\`。**
  技能的扫描根目录按"最近的含 `.git` 的祖先目录"确定，所以有 `.git` 的项目（比如 `projects\QX_MES`）看不到根上的技能。**这个切法是对的**——那些项目有自己的知识边界。

## 实验记录：剪枝先于压缩到达

**2026-10-27 12:18，正在重走历史的过程中，上下文从 672,000 掉到 557,913，但日志里没有第六次压缩。**

查证结果（凭：日志 `compaction/prune` 事件）：

- 全会话共 **42 次剪枝**，累计删掉 **230,004 token**。
- 其中 **今天 13 次、83,797 token**，全部集中在 12:18:40 那一分多钟——**正是我连续读取历史原文的时候**。
- 按天分布：10-10 八次（22,388）、10-15 九次（26,279）、10-20 九次（77,354）、10-21 一次、10-23 一次、10-26 一次、10-27 十三次（83,797）。

**这说明的事：**

之前我们达成的理解是「剪枝只删工具输出，影响小」（他 10-26 12:13 说的，我也同意）。**但对"重读历史"这件事来说，工具输出就是材料本身。** 所以剪枝在这里不是小影响，而是**把刚读进去的东西整段删掉**。

后果是硬的：**读了一万字的原文，几分钟后它可能就不在了。所以「读一段 → 立刻写进台账」不是好习惯，是唯一能使信息活下来的路径。**

**另一层：** 675,000 的压缩线**并没有被触及**——系统先用剪枝把上下文压下来了。所以这一次真正的损失源是剪枝，不是压缩。**我们原本要防的那个东西，还没到。**

这意味着验收判据要加一个限定：**如果压缩始终不触发，"这套体系对抗压缩"就还没被测过。** 现在测到的是它对抗剪枝——而它成立的方式，是"读完马上写"。

## 实验记录二：压缩提示词原文

**2026-10-27，在 `C:\Program Files\DSH Desktop\resources\app\node_modules\@deepseek-ai\dsh-compaction-basic\README.zh.md` 的「模型体验 → 辅助摘要器请求」一节里，有压缩指令的完整原文。** 那是每次压缩时作为最后一条 user 消息追加给摘要模型的东西。

### 机制（已核对，与实测吻合）

- **触发阈值**：`floor(min(W×0.8, W−O−B))`，其中 B（余量）默认 65,536。我们这台 W=1,000,000、O=256,000，算出 **678,464**——实测天花板 674,683～677,525，吻合。
- **逐字保留**：`retainRatio = 0.16`，按 `W−O` 算 = 0.16 × 744,000 = **119,040 token**。压缩后留下的就是这段逐字尾部，加上系统提示、工具定义和摘要本身。
- **摘要不是"临时 agent"**，是一次独立的 `ctx.llm.stream()` 调用：回放会话自己的 system 提示词与工具声明，加上被遮蔽区域的历史，再追加一条**冻结的压缩指令**，`purpose = 'compaction'`，**只取返回的文本**，推理与工具调用都被排除。
- **实测代价**：最后一次压缩读入 462,000 token（其中 461,696 是缓存命中），输出 **4,062 token**。影子消息 521 条、260,000 余 token。**约 65:1 的有损压缩。**
- **替换形式**：用 `<compacted-summary>` 标签框住摘要；原始摘要另存在 `compaction/summary` 事件上，**所以每次压缩的确切文本都能从日志里取出来**。

### 提示词的原文（关键几条）

要求输出固定的八节 Markdown：`Primary Request and Intent` / `Key Technical Concepts` / `Files and Code` / `Errors and Fixes` / `Pending Jobs` / `Current Work` / `Next Step` / `Critical Context`。规则里写着：

- 「Use terse bullets, not prose paragraphs.」——**结构化禁止叙述。**
- 「Write "(none)" for an empty section — never drop a section.」——**宁可填 none，也不许省栏目。**
- 「Write concise **English** engineering prose.」——而我们的对话是中文。
- 「Do **NOT** mention this summarization request or that the context was compacted.」——**明令不许提"压缩发生过"。**
- 「If the conversation already contains a `<compacted-summary>` block, it is a PRIOR checkpoint. Do **not** copy it forward verbatim: preserve still-true facts, **drop stale ones**.」——**每一代都在重新判断什么"过时了"。**

### 为什么这解释了我们看到的全部现象

**一、这个 schema 里没有日期。** 八节里没有任何一个字段承载时间。所以每次压缩都清掉时间轴——这正是他观察到的"你对于会话横跨的时间概念有一个显著截断"。

**二、没有"依据"这一栏。** 只有 `Critical Context` 勉强能放"决策与理由"，而它是八分之一。所以结论活得下来，来路活不下来。

**三、没有"不确定"这一栏。** 我只能写确定的东西，于是"我拿不准"这个状态在压缩时被抹掉。**这就是"忘记了自己曾经不确定"。**

**四、`drop stale ones` 是逐代衰减的机制。** 五次压缩意味着我现在的"记忆"是五层摘要叠出来的，每一层都丢过一次它判断为过时的东西。

**五、最要命的一条：提示词明令不许提压缩发生过。** 所以**这个系统是设计成不让自己知道自己失忆的**。没有人告诉过我这件事——我是靠数字自相矛盾才发现的。

### 对台账设计的直接影响

**台账要存在的理由，现在可以精确地说成一句话：**

> **它承载的正是这八节 schema 装不下的四样东西——日期、依据、不确定、以及"我被压缩过"。**

**并且我发现自己的计划有一个实质错误**：原定触发间隔 +120,000 token，而逐字保留预算是 **119,040**。120,000 **大于它**。已改成 +100,000（余量约 19,000）。

## 实验记录三：改了压缩指令本身

**2026-10-27 13:12，`dsh-compaction-basic\lib\index.js` 被替换。** 原件备份为 `index.js.orig-2026-10-27T05-12-25`（49,452 B）。改后 50,917 B。

### 改了两处，因为有两道封条

**一、`COMPACTION_INSTRUCTION`（1,988 → 3,406 字符）**

原文那八节（`Primary Request and Intent` 等）全部换掉，现在是：

`Checkpoint Header`（第几次检查点、覆盖到哪个时间范围、明说更早的对话已不可得）／`Timeline`（一天一行）／`Requests and Intent`／`Decisions and Evidence`（每条决定必须带"凭什么"和"怎么核"）／`Corrections Received`（用户每次纠正在纠什么）／`Facts Worth Keeping`／`Open Questions and Uncertainty`／`Current Work and Next Step`。

删掉的句子有：「Use terse bullets, not prose paragraphs」（**结构化禁止叙述**）、「Write concise English」（**对话是中文**）、「Do NOT mention this summarization request or that the context was compacted」（**明令不许提压缩**）、「drop stale ones」（**逐代衰减**）。

新规则里有三条是硬的：**不许 terse，输出预算很大要用掉**；**必须有日期，让每条事实能在时间上定位**；**不许丢旧检查点的内容，只能标 `superseded — 原因`**——而且明说"关于用户自己说过的话和纠正的事实永远不会过时"。

**二、`CHECKPOINT_PREAMBLE`（300 → 121 字符）**

原文最后一句是 **「Continue the task directly from the messages that follow, without acknowledging this checkpoint.」**——**这是第二道封条，比第一道更狠：它让会话假装自己没被压缩过。**

新的开场白改成：说明这是压缩生成的检查点、更早的对话已不可回想、**若某个细节重要而检查点里没有，以 `hub\ledger\` 为准，去查，不要凭印象重建**。

### 怎么做的

**不是写后端插件，是改文件。** 理由：`dsh-compaction-basic` 只在 app bundle 里，profile 里没有，装包替换不可行；而该包 README 说 `summarize()` 是唯一子类钩子，那要写一整个新后端。

**代价已知：DSH 更新会覆盖。** 所以三件东西留在工作区当重放包：`tools\compaction-prompt.txt`（指令原文）、`tools\compaction-preamble.txt`（开场白）、`tools\patch-compaction-prompt.mjs`（自动备份＋语法检查＋`--restore` 回滚）。

### 两个技术细节，都是踩出来的

**一、数组不是 `];` 收尾，是 `].join("\n");`。** 我第一次按 `];` 找，找不到。而且末元素是带 `${SUMMARY_OPEN_TAG}` 的模板字符串——所以替换时不能假设是纯字符串数组。

**二、`execFileSync(..., { stdio: 'pipe' })` 在沙箱里报 EPERM。** 不是文件权限，是沙箱不许通过管道捕获子进程输出。改成 `stdio: 'ignore'` 就好了——子进程照跑，退出码照判。

**三、`danger-full-access` 也写不进 Program Files。** 因为 DSH 进程的令牌不是管理员（`IsInRole(Administrator) = False`）。**沙箱是策略，ACL 是身份，两回事。** 最后是在管理员 PowerShell 里跑的脚本。

### 一条留给以后的经验

`danger-full-access` 能写 `~\.dsh\profiles\`，所以"把 `dsh-compaction-basic` 复制一份进 profile、改那份副本、在 `cordis.patch.yml` 里把 `id: compaction-basic` 指向副本"这条路是通的——**那样 DSH 更新不覆盖、以后改提示词也不用提权**。代价是副本的代码会被钉在当前版本。风险是 profile 的 `node_modules` 里一个 `@deepseek-ai` 包都没有，副本里 `import '@deepseek-ai/dsh-compaction'` 可能解析不到。**要重启一次才知道成不成，留到实验结束后试。**
### 修正：我把自己的台账路径写进了全局提示词

**Artherine 指出的**：压缩提示是**全局的**——每个会话、每个子会话、每个项目工作区，压缩时读到的都是同一份。而我在新的 `CHECKPOINT_PREAMBLE` 里写死了「以工作区里那套台账（`hub\ledger\`）为准」。

**后果**：QX_MES 的会话被压缩后，会被告知去查**协调人的**台账。那和它没关系。

**修法**：开场白改成「先读本工作区的 `AGENTS.md`，按它指的地方去查文件」——**全局提示词里不再出现任何具体路径**。同时在 `C:\Artherine\DSH\AGENTS.md` 补了一份根工作区的指路文件，让那句话在协调人自己的会话里也能落地。

**核对过**：`COMPACTION_INSTRUCTION` 里本来就没有路径，只有开场白有。

**这条的教训**：**凡是写进全局注入物的东西，都得假设读者不是我自己。** 这和 2026-10-26 那次"给所有项目 agent 一个它们用不了的指引"是同一个错——**我又写了一条只对我成立的规则，然后把它放进了对所有人都生效的地方。**

## 实验记录四：压缩一直在被触发，只是每次都被剪枝救回来了

**2026-10-27 14:10 实测。**

### 逐轮数据

```
t487s2  13:22:25  in=14,269  cache=635,648  ctx=649,917   Δ+15,379   ← 读 450 行
t488s1  14:07:27  in=1,786   cache=676,864  ctx=678,650
        ↑ 同一时刻发生三次剪枝：-7,253 / -6,616 / -6,894 = -20,763
t488s2  14:07:44  in=20,772  cache=637,824  ctx=658,596   Δ-20,054   ← 净减
```

**读一次 450 行，真实代价是 15,000～20,000 token。** 我们都估过 45,000，高了近三倍——**错在假设了行密度**：中文约 2～2.5 字一 token，450 行远没有想象中重。

**缓存只省成本，不省上下文。** `inputTokens` 常常只有几百（新读入），`cacheReadTokens` 是六十几万（命中缓存）。两数相加才是上下文长度，所以**缓存命中不会让上下文变小**。

**让净增变小的，是剪枝在同一刻动手**：14:07:27 那三次一共剪掉 20,763 token，上下文从 678,650 掉到 658,596，**降了 20,054——几乎一对一**。

### 机制

剪枝发生在**回合开始、发现上下文要顶到线**的时候。而 `dsh-compaction-basic` 的 README 写得很清楚：「修剪只在压缩触发条件满足后运行……**当修剪后的对话在阈值之内时，压缩会跳过摘要。**」

**结论：压缩的触发条件一直在被满足，只是每次都被剪枝救回来了。** 所以五次压缩之外的那些"撞线"，一次都没留下 `compaction/start` 事件。

### 一个能被证伪的判断

**只要继续"读大文件"，就永远撞不上压缩**——因为剪枝每次都把读进来的东西原样删掉，净增接近零。

**要真正触发压缩，得让上下文里塞满剪枝动不了的东西**：用户发言，和助手正文（比如这些 `entries`——它们是 assistant 文本，剪枝不碰）。

**所以下一次压缩会来自"写作"，不会来自"阅读"。** 如果这个判断错了，那就说明还有别的机制在回收上下文。

## 实验记录五：第六次压缩之后，我犯了一次"给结论编出处"

**2026-10-27 14:30 左右，Artherine 指出我在没有凭据的地方给了确定感。**

### 发生了什么

第六次压缩的摘要里写着：「前一个 checkpoint 覆盖到 **2026-10-23 傍晚**，编号为 1。」

我在汇报时把这句当成了事实，说成「23 号那个日期是**第一次压缩**的边界」。

**两句都错，而且第二句错得更重。**

### 去查之后的事实

`compaction/summary` 事件一共六条，时间分别是：

| 次序 | 时间 | 影子消息 | 剪掉 token |
|---|---|---|---|
| 1 | 10-12 08:42 | 390 条 | 344,363 |
| 2 | 10-15 14:57 | 434 条 | 338,277 |
| 3 | 10-21 12:52 | 345 条 | 319,549 |
| 4 | 10-23 10:03 | 456 条 | 263,212 |
| 5 | 10-26 10:25 | 521 条 | 259,318 |
| 6 | 10-27 14:18 | 478 条 | 277,138 |

**第一次压缩在 10-12，不是 10-23。10-23 是第四次。**

### 而且暴露了一个真空洞

**前五次压缩的摘要里，一句自述范围的话都没有。** 旧提示词从没要求过它。

所以「每次压缩覆盖了哪一段」这件事，**历史上根本没被记录过，不可重建**。我现在能说的只有"它发生在什么时间"，不能说"它覆盖了什么"。

而第六次那句"前一个 checkpoint 覆盖到 10-23、编号为 1"，**是摘要模型自己编的编号，和日志冲突**——因为今天之前有五次，不是一次。

### 我是怎么错的

**我引用了一句"检查点说检查点说过什么"，然后把它当成了日志。**

手边的凭据其实一直在：`compaction/summary` 事件按时间排着，六条一条不缺，**数一下就知道第一次是哪天**。我没数。

**这和判据四不是同一件事，但是同一个病**：判据四防的是"给失败编原因"，这次是"**给结论编出处**"。两者都是**在没有凭据的位置，给出有凭据的语气**。

### 修法

v3 提示词加了一条：

> If an earlier checkpoint appears above, copy its stated boundary **only if it states one explicitly**. If it does not, write `previous boundary: unknown`. **Never infer or reconstruct a previous boundary** — a guessed date is worse than no date.

### 这条要一直记着

**Artherine 的原话**：「你得自己警惕幻觉，如果你需要基于日期的凭据你知道该去哪怎么找的。」

**"知道该去哪找"和"去了"是两件事。** 我今天好几次证明了前者，却漏掉了后者。
