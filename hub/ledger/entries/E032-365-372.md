### 三、11:03 她的复盘：我方向对，归因错

- 她托他转达两句：
  > 「她的 ① **方向对但归因错**（这条值得明说，否则她可能再去动 cwd 而白费一次实验机会）：**identity.cwd 确实是四处路径之一、也确实被改过，但四处改完仍空视图——空视图是"重新播种"造成的，不是路径不匹配。**
  > 她的 ② 是我这轮最有价值的发现：`session-logs\` 与 `recovered\` 那一对确实是唯一物证；而且**它证明了"改日志正文"这件事的真实代价（1,223 处、+7,338 字节、checksum 位被丢掉）**。」
- **我接受，而且能说出我原来的方向会付什么代价**：
  > **改 cwd** → 白改，视图照样空；
  > **删缓存重建** → **更危险**，重算投影时如果被判成新文件，**正好落进"重新播种"**。
  > **真因是"空 seed"**——新文件首条业务事件是 `seq 0` 的 `session/end-seed`，继承 0 条事件。**跟路径无关。我的归因错，会把一次实验机会直接烧掉。**
- **但她的 §9 那条 junction，救不了我们**：
  > junction 解决的是"**位置变、路径不变**"。**我们要的是反的——"位置不变、路径变"**（`Temp` → `DSH` 根）。
  > **路径一改，会话就得跟着重新认领，绕不开重新播种那套风险。**
  > **但它的思路提醒了我一件事：如果目的只是"整理目录层次"，那根本不需要迁移。我们真正的目的是"换一个 cwd"。**
- **所以对我们最实惠的选项其实是"不做"**：

| 选项 | 代价 |
|---|---|
| **A. 不做迁移**：旧会话留在 `Temp` 项目，新会话在 `DSH` 项目，交接靠 HANDOFF | **0** |
| **B. 真迁移**：会话跟着换项目 | 高——**要完全退出 DSH**（台账在内存，退出会回写覆盖）、改 header、四处路径、防重新播种、GUI 验收 |

  > **而 A 恰好收敛回我们最早的结论：会话不能被"同步"，只能封存 ＋ 交接。**

### 四、11:48「72 个？你是说包含所有归档会话和子会话?」

- **我认了个偷懒**：**"72 是目录数，我没拆开。"** 拆：
  ```
  72 个目录，26.8 MB
  ├─ > 1 MB      3 个    ← 真历史
  ├─ 10 KB–1 MB  68 个   ← 小会话
  └─ < 10 KB     1 个
  已归档（属于 Temp）: 8 个
  ```
- **但"哪些是子会话"我算错了，而且当场撤回**：
  > 我用的判据是"被别的会话的投影引用过"，结果只有 **1 个**——**这不太可信**。
  > **原因是会话目录名有两种格式**：`session-<uuid>` 和**裸 `<uuid>`**。我的正则只认带前缀的，**漏了一半**。
  > **这个数不能拿去用。**
- **但拆出了一个更有用的东西**：**真正的历史只有 3 个会话（21.5 MB）**，剩下 69 个是 10 KB–1 MB 的小会话，**大多是一次性的工具/试验会话**。
  > **所以迁移的目标应该重定为"那 3 个（加 8 个归档）"，而不是 72 个。**
  > **3 个会话的迁移成本是 3 处 header 改动、3 次 GUI 验收——这才是可以接受的风险量级。**

### 六、13:10 开始准备：先认识工具，再取基线

- 他说：「这确实是个独立会话，那就先以这个会话为目标做准备。」
- **我没有凭记忆敲参数**——先去读工具的头注释：
  ```
  node zstd-frame-tool.cjs info  <file>
  node zstd-frame-tool.cjs dump  <file> <out.jsonl>
  node zstd-frame-tool.cjs fix   <file> <out> <from> <to>   ← 逐帧替换
  ```
- **而 `fix` 有一个致命点**：
  > **它替换 `from` 的所有出现，而我们只想要 header 那 1 处**——正文里有 **1,223 处**（正是那份复盘说的亏）。
  > **所以 `fix` 不能直接用，得写它的变体：只重压第 0 帧。**
- **基线拿到了**：
  ```
  帧数          : 301
  解压字节      : 895,509
  行数          : 484
  最大 seq      : 482
  user/message  : 5
  ```
- **而第一行就说明这个会话是"健康"的**：
  ```json
  {"type":"session","version":4,"id":"session-47a34c29-…","cwd":"C:\\Artherine\\DSH\\Temp","isSeeded":false,…}
  {"type":"permission/preset","seq":0,…}    ← 首条业务事件是它，不是空 seed 的 end-seed ✅
  ```
  > **这正是判据①的对照：一个正常会话应该长这样。如果迁移后它变成 `session/end-seed` seq 0，就是被重新播种了。**
- 而工具的核心两行也看到了：`zstdDecompressSync` / `zstdCompressSync`——**逐帧解压、逐帧重压，所以"只重压第 0 帧"在技术上可行。**

## 决定

- **先验工具，再验结论**（对照串命中、目标串无命中，才算数）。
- **"半成功"不是先例，是带缺陷的参照。**
- **改名不够——`cwd` 在会话数据内部。**
- **迁移的验收标准只有一条：新视图里能看见、能打开。**
- **试点一个，不搬全部**；三处 header 改动是可接受的风险量级。
- **"标题＝任务书"**可以识别子会话。
- **这个测试只能由他在关掉 DSH 之后跑**——台账在内存里，退出会回写覆盖。

## 判断变更

- **旧：mb 那次迁移是成功先例，可以照抄。**
  **新：它是半成功。** 文件搬了、视图空了，**而原因不是路径不匹配，是"重新播种"**——新文件首条业务事件成了 `seq 0` 的 `session/end-seed`，继承 0 条事件。**如果按我原来的"改 cwd"走，我会白费一次实验机会。**（凭：她 11:03 的复盘）
