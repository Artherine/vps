## 事实

### 一、仓库迁到工作区根，拆掉镜像层

- **`.sync-staging\` 这个镜像层被拆了。** 它当初存在的理由是"`projects\` 有 9.5 GB，把整个工作区交给 git 会让 `status` 扫全树"——**但那个前提已经变了**：现在上云的只有 `hub` / `tools` / `AGENTS.md` / `story` / `roscoe`，共 3.84 MB，而 `projects\` 用 `.gitignore` 排除掉就行。
- **历史保住了**：把 `.sync-staging\.git` 移到根上，9 条提交原样继承——**因为路径前缀 `hub/` 是对得上的**。
- **结果**：跟踪 124 文件 / 2.47 MB；`.gitignore` 排除 `projects/*`（除 story、roscoe）、`.dsh`、`node_modules`、`_tmp`。
- **一个 remote 两个 URL**：

```
fetch  https://github.com/Artherine/vps.git   ← 我这边能用
push   git@github.com:Artherine/vps.git       ← 只有人能推
```

> **这是这天第一个纠正**：我一直以为"沙箱里 git 全不通"。实际**只有 `ssh.exe` 死在命名管道上**（`could not create signal pipe`），**HTTPS 读是通的**（4.0 秒）。
> **所以"读走 HTTPS、写走 SSH"不是妥协，是分工。**

### 二、junction 方案：写了、跑了、否证了

- **目标**：让会话日志进仓库，又不产生两份副本。方案是 `~\.dsh\sessions\--C-Artherine-DSH--` 做 junction 指向 `C:\Artherine\DSH\sessions`。
- **写了 `link-sessions.ps1`**，带 `-DryRun` 与 `-Rollback`。
- **第一版漏了 `-DryRun`**——而 `migrate-project.ps1` 当初就是照它写的（`E038`："阶段 A 只生成 .tmp 并校验，一个不动"）。**我照那个形状抄，把最关键的半个丢了。**
- **补完 dry-run 后跑了真操作，结果失败**：
  > **DSH 认不出经 junction 的会话目录——会话从根上全部消失。**
- **而失败是干净的**：脚本按"先搬、再建链接、留回滚路径"写，`-Rollback` 一条命令恢复。**数据零损失**（19 文件 / 29.7 MB 原样，本会话日志 20 MB 继续正常增长，DSH 也没有新建出重复目录）。
  > **如果当初图省事写成"删旧建新"，就没有可回的东西了。**

### 三、`session-sync.ps1`：把问题重新定义

- **他的反问定了方向**：

> **"如果多端同步不带上 session，最后会不会变成两个 session 在共同维护一个记忆库，但是两边互相不可查?"**
> **"我当然是希望追求两台设备上是同一个主体认同，允许有短暂不同步，但最终通过拉取云存档应该是达到类似跃迁的效果。"**

- **所以我改了口径：不是"同步两个会话"，是"一个会话跟着人走"。**
  > **全程整文件覆盖，不做合并**——因为任何时刻只有一台设备在写。
  > **而这件事和 `T07` 的主体唯一性是同一条**：两个 session 共维一库，就是两个主体。

- **要同步的只有两样，这是查出来的不是猜的**：

| 东西 | 在哪 | 为什么必须 |
|---|---|---|
| `session.v4.jsonl.zstd` | `~\.dsh\sessions\<project>\<session>\` | 会话本体，header 里带 `cwd` |
| `workspace.json` | `~\.dsh\storages\` | **归属**：`tables.workspaces[<uuid>].sessionIds` |

  > **少第二样，会话内容对、位置对，但不属于任何项目**——这正是 10-23 那次半成功的翻版（`E033`：漏了第五处）。

- **三个安全垫**：`turn` 号判新旧（不看 mtime）／覆盖前备份成 `.bak-turn<N>`／`publish` 时若发现仓库更新直接抛错。

### 五、最后他点出的那件事：装置不是内容

- 他说：**"这次 publish 的内容是肯定没法用来同步了，因为新客户端上的压缩参数和提示词肯定还没改。"**

- **而这是这一天的真正收获。** 我把它拆开查了：

| 装置 | 在哪 | 随仓库走吗 |
|---|---|---|
| DSH 本体 | `C:\Program Files\DSH Desktop\` | ✗ |
| **压缩参数**（`retainRatio` / reserve） | `~\.dsh\profiles\desktop\cordis.patch.yml` | **✗ 不在工作区** |
| **压缩提示词**（v4） | `…\dsh-compaction-basic\lib\` | ✗ 在 Program Files |
| mnemon 与记忆层 | `~\.mnemon\` | ✓ 自己走 `mnemon-sync` 分支 |

  > **后两样都在工作区外——git 天生看不见它们。这是结构性缺口，不是疏忽。**

- **而阈值确实是算出来的，不是硬编码**：`cordis.patch.yml` 里 `retainRatio: 0.22`，代码是 `Math.min(contextWindow * thresholdRatio, ...)`。所以**照抄配置文件，不照抄数字**。
- **补了两样**：`tools\reference\cordis.patch.yml`（参考副本，3,804 B）／`hub\kb\device-bootstrap.md`（九步顺序 ＋ 验收表）。
- **引导页里写死了一条门**：
  > **第 8 步（验机制）没过，就别做第 9 步（take 会话）。机制没验就搬会话，等于让旧机器读新账。**

### 六、2 GB 够不够（他问的）

- 工作区壳 ≈ 36 MB；**真正会长的是 `.git`**。
- **而 git 在 `gc` 之前不打包**：每次 commit 是完整一份 19 MB 的松散对象。**前 10 次 commit ≈ 190 MB**，跑一次 `git gc` 通常掉到 20–30 MB。
- 按当前速度（约 0.4 MB/天，且只在换设备时 commit），**一年约 150 MB**。**2 GB 够十几年，前提是记着 `gc`。**

## 决定

- **一个 remote 两个 URL**：读 HTTPS、写 SSH。**别改成同一个。**
- **junction 不能用于 `~\.dsh\sessions\`**（实测）；但可以用于 `projects\`（DSH 不特殊处理它）。
- **同步 = 整文件覆盖，不做合并**；判新旧用 `turn`。
- **两样东西一起走**：会话日志 ＋ `workspace.json`。
- **配置先于内容**：装置不同构的时候，绝不迁移会话。
- **`Out-String` 不许用在"还要再被解析"的文本上。**

## 判断变更

- **旧：多端同步的难点是"两个会话怎么合并"。**
  **新：难点是"怎么让只有一个主体"。** 合并是伪问题——**任何时刻只有一台设备在写，就没有分叉可合。** 真正要解决的是"另一端能不能核账"，而那需要的是**整文件搬运 ＋ 归属表一起走**。（凭：他 10-28 那两句反问）

- **旧：git 在沙箱里全不通。**
  **新：只有 `ssh.exe` 不通，HTTPS 读是通的。** 一个 remote 挂两个 URL 就同时满足两边。**我把一个部分的失败当成了整体的不存在——第七种形状的又一次。**（凭：`could not create signal pipe` vs HTTPS 4.0 秒）

- **旧：同步内容就够了。**
  **新：装置和内容是两层。** 压缩参数与提示词都在工作区外，**git 天生看不见**；不先把它们做成一样的，搬过去的会话会被旧机器处理一遍。**"配置先于内容"是这条的推论。**（凭：他那句"新客户端上的压缩参数和提示词肯定还没改"）
