### 三、装 mnemon：三层因果链

- 起点是他一句问题：「那看来现在的重心就是为什么找不到mnemon 脚手架了。」
- 第一层——**为什么找不到**：设计如此。插件 README 原话「**Mnemon Native 使用单独安装的 `mnemon` CLI**……**npm 默认安装包两者都不包含。**」所以装的是驱动骨架，不是后端。
- 第二层——**为什么装不上**：两个叠加的障碍。
  - 代理变量指向一个坏代理（`127.0.0.1:7897`），`curl -x` 返回 000，`--noproxy` 返回 200。
  - `.npmrc` 里 `prefix` 和 `cache` 都写死到 `C:\Program Files\nodejs\...`，那个目录**根本不存在**。
- **他给了最后一块拼图**：「因为正常来说我的其他开发工具都是用的管理员用户打开的，偏偏dsh是普通用户吧。」——同一份 `.npmrc` 在管理员终端里能写，在 DSH 里必然 EPERM。
- 我走的是零配置路线：装进插件本来就会搜索的 `%LOCALAPPDATA%\Programs\mnemon`，不动 npm 全局 prefix、不动 PATH。装完 `mnemon version 0.2.9`，插件报 `healthy=true`。
- 然后一串能力依次解锁：记忆空间创建 → 写入 → **语义召回 recall** → **图遍历 related** → **文档就地更新 update** → **文档归档 archive**。
- 顺带发现两件事：①**归档不是删除，是"双址冷藏"**——先往记忆空间落一份冷参考（带 Document ID + 冷路径 + 内容 SHA-256），再把文件移进 `documents/archived/`；②`related` 显示那两份冷参考**自动挂上了 entity 边**，归档的东西能被图遍历找到。

### 四、他纠正我的第二次：npm 版本被钉死了

- 15:34，他让我改 `.npmrc`，我建议指向 `C:\Programs\npm_store\npm_global`（真实 store、机器 PATH 上、普通用户可写）。
- 15:38，他问：「听上去变成系统默认指定固定的npm版本实现了？ nvm的镜像实现才是应该保留的吧。」
- **他是对的，我上一轮错了。** 我把 npm 启动器的逻辑挖了出来：

  ```cmd
  FOR /F ... IN ('CALL "%NODE_EXE%" "%NPM_PREFIX_JS%"') DO (
    SET "NPM_PREFIX_NPM_CLI_JS=%%F\node_modules\npm\bin\npm-cli.js"
  )
  IF EXIST "%NPM_PREFIX_NPM_CLI_JS%" ( SET "NPM_CLI_JS=%NPM_PREFIX_NPM_CLI_JS%" )
  ```

  **npm 会先算 prefix，如果 prefix 下存在自己的 `node_modules\npm`，就用 prefix 里那份，而不用当前 Node 自带的那份。** 那个 store 里有 npm 11.1.0，而活动 Node（v22.19.0）自带 10.9.3——所以我一改 prefix，`npm -v` 就从 10.9.3 变成 11.1.0，**npm 版本被钉死**，而 npm 11 要求 Node ≥ 20.17，在 v10/v11/v16 下会直接炸。
  更讽刺的是：**那个"僵尸 prefix"其实在无意中起了保护作用**——因为它指向不存在的目录，shim 每次都回退到当前 Node 自带的那份，npm 版本天然跟着 nvm 走。
- 修法：`prefix` 写**符号链接** `C:\nvm4w\nodejs` 而不是某个具体版本目录——这个"固定值"会随 `nvm use` 自动指向当前版本，既有镜像语义又不需要动态配置。验证：`npm -v` 回到 10.9.3，`npm prefix -g` 是符号链接，`npm view` 不再 EPERM。
