# T06　工作区与迁移

> 一行摘要：**连续性不在会话里，在文件里；而迁移的核心不是"改路径"，是"改归属"。**

## 当前定论

**一、连续性不在会话里，在文件里。** 这条是 `T07` 和 `T06` 共用的地基，但在这里它有个具体形状：
- 会话绑在进程和机器上，**没有"继续一个会话"这回事**——只有"开一个新会话，读上一个人留下的东西"；
- **所以多端同步的正确形态是"同步卷宗 ＋ 遗书"，不是同步会话。**
- 最简形式（10-23 他自己给的）：**两台设备不会同时启动**，所以并发这个唯一难的部分直接消失，剩下的只是**备份 ＋ 比对**。

**二、迁移的核心是"归属"，不是"路径"。**
- 会话的 cwd 存在**五处**：会话目录名（`--<规范化cwd>--`）、日志 header 的 `cwd`、`identity.cwd`、投影缓存、以及 **`workspace.json` 的 `sessionIds`**。
- **第五处才是"归属"本身**——改对前四处，会话仍然会落进"未分组"。
- 目录名**不是 hash，是"规范化 cwd"**（`\`→`-`、`:`→`-`、前后加 `--`）——**一个词之差，整个"不可改变"的前提就塌了。**

**三、铁律：封存 → 备份 → 搬 → 验证。** 搬的时候不能有会话在写；**先组织成项目结构，再切 cwd**（顺序反了就断在那儿）。

**四、迁移的验收标准只有一条：新视图里能看见、能打开。** 而"半成功"不是先例，是带缺陷的参照——mb 那次文件搬了、视图空了，**真因是"重新播种"不是路径不匹配**。照抄会白费一次实验机会。

**五、技术细节（都是踩出来的）。**
- **只重压第 0 帧**，正文一个字节不动；**`checksum` 必须保住**（上一次迁移丢了它）；
- 脚本要 **UTF-8 带 BOM**，并用 **PowerShell 5.1 本体**做解析检查；
- 守卫要抓 `DSH Desktop` 进程——**三个都没了才算完全退出**（台账在内存，退出会回写覆盖）；
- **"回滚"只是一个方向**，机制与迁移相同——别用"还原"这种词，它暗示一个并不存在的过去状态。

**六、"换工作区"不需要搬任何文件。** 只要下一个会话在 `C:\Artherine\DSH` 开起来，`Temp` 就自动变成它的子目录。**我自己那一步根本不必做——只要 cwd 变了。**

**七、任何"前后对比"必须同源同刻。** 18 vs 19 那个数不是错误，是时间——**我拿迁移前的清单比迁移后的文件**。同一个毛病在 mb 那次也犯过（"变大了 129 KB"，其实是他打开过它）。

**八、"留本地"与"上云"是两个维度，不能合并成一个问句。**
- 判据：**同步的是"丢了要花大代价才回来"的；不同步的是"丢了重拿很便宜"的。**
- 而云仓库有预算：`hub\` 约 780 KB 上云；`projects\` 9.9 GB 里只有 story／roscoe 该上；dnd、node_modules、日志副本都不上。

## 九、会话日志要不要进版本管理（2026-10-27 定，未实施）

**结论：要。** 而原来的"不进"是错的，错在一条被我用了一半的前提。

**我原来的论证**：「没有'继续一个会话'这回事，所以日志不可以被接管，所以不进版本管理。」
**错在哪**：那条讲的是**两个活着的会话不能合并**。它不覆盖**一个会话被搬走**——而 `migrate-session.ps1` 就是干这个的，**我们自己验过两次**（`session-47a34c29` 迁成功、回滚一次、五处路径全对）。

**而真正逼出这个结论的是另一个问题**：

> **如果多端同步不带 session，会不会变成两个 session 共维一个记忆库、而两边互不可查？**
>
> **会。而且后果不是"分叉"，是"审计链断一半"。**
> 台账的全部前提是"E 是来路，可回查"。两边各写各的 E，**每一侧都有另一半条目的来路躺在自己读不到的那个日志里**。那不是两份不一致的记忆，是**一份谁都只能核一半的记忆**。

**解法：让 sessions 住在仓库里，但仍然出现在 DSH 期望的路径上——用 junction。**

```
~\.dsh\sessions\--C-Artherine-DSH--\   ← junction
                        ↓
C:\Artherine\DSH\sessions\             ← 真实目录，在仓库内
```

- **一份数据，两条路径**——不做镜像，不产生"哪边是权威"的问题（这正是 `.sync-staging` 被拆掉的原因）；
- Windows 的 junction **不需要管理员权限**（符号链接才需要）；
- git 只跟踪真实目录，DSH 照旧按原路径读写。

**阻塞：这个动作必须在 DSH 完全关闭时做。** 当前会话正写在那个目录里——**搬它等于行驶中换轮胎**（`E033` 的原话）。所以这是**下次开工的第一件事**，不是现在。

### 实测结果（2026-10-27 当天）：**junction 方案否证**

**跑了，失败了，回滚成功。**

- 脚本执行完毕后，**DSH 根目录下会话全部消失**——DSH 认不出经 junction 的会话目录；
- **数据零损失**：回滚后 19 文件 / 29.7 MB 原样，本会话日志 20 MB 继续正常增长，DSH 也没有新建出重复目录；
- **失败是干净的**：没有删任何东西，只是"看不见"。`-Rollback` 一条命令恢复。

**为什么它能干净失败**：脚本按"先搬、再建链接、留回滚路径"写——**如果当初图省事写成"删旧建新"，就没有可回的了。**

**所以：会话日志不能靠 junction 进仓库。** 剩下两条路：
1. **复制一份进 `sessions\`**——要接受两份副本，必须写清哪份是权威（活件在 `~\.dsh\`，副本只读、只用于同端再取回）；
2. **不搬，只导出快照**（`/export` 的 ZIP），离散、不可变、不进日常 diff。

**而"两个 session 共维一库、互不可查"这个失效风险仍然存在**——本节开头那个判断没有被否证，只是解决它的手段被否证了。

**另一条待验仍未答**：git 对 zstd 追加文件到底 delta 得怎么样。
## 十、装置不是内容（2026-10-28）

**搬会话，不等于搬"读会话的那套机制"。**

| 装置 | 在哪 | 随仓库走吗 |
|---|---|---|
| DSH 本体 | `C:\Program Files\DSH Desktop\` | ✗ |
| **压缩参数** | `~\.dsh\profiles\desktop\cordis.patch.yml`（`retainRatio: 0.22` 等） | **✗ 不在工作区** |
| **压缩提示词**（v4） | `…\dsh-compaction-basic\lib\` | ✗ 在 Program Files |
| mnemon 与记忆层 | `~\.mnemon\` | ✓ 自己走 `mnemon-sync` |

> **后两样在 `~\.dsh\` 和 `Program Files\`——git 天生看不见它们。这是结构性缺口，不是疏忽。**

**推论：配置先于内容。** 机制不同构的时候迁过去，第一件事就是被旧机器处理一遍——**v4 提示词的全部意义会被那台的 v1 抹掉。**
